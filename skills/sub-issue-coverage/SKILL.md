# Sub-issue Coverage Check

親Issueの要件を、子Issueのどれが担当しているかを一行ずつ照合し、担当のない要件・使う側のいない成果物・共有状態を壊す検証手順を、**子Issueの作業が始まる前に**見つける。

子Issueを閉じる前の確認では遅い。その時点では実装もリリースも終わっている。

## いつ使うか

- 子Issueに分割した直後、作成する前（`sub-issue-maker` / `pbi-task-split` の分割案に対して）
- 子Issueを作成した直後（`pbi-sub-issue`）
- 子Issueを持つ親Issueの監督・割り当てを始めるとき（`claude-tmux-pm` / uuter の監督）。最初の子Issueを渡す前に1回
- 親Issueに決定事項が追加されたとき（本文の更新・コメントでのオーナー決定）

## 手順

### 1. 材料を集める

```bash
gh issue view <親> --repo <owner>/<repo> --comments
gh api repos/<owner>/<repo>/issues/<親>/sub_issues -q '.[]|"#\(.number) \(.state) \(.title)"'
gh issue view <子> --repo <owner>/<repo> --comments   # 子Issueすべて
```

コメントで決まったこと（日付付きのオーナー決定など）も要件に含める。本文だけを見ない。

### 2. 親の要件を一行ずつに分ける

親Issueから、次をそれぞれ独立した行として抜き出す。各行には親Issueの原文を引用して、出どころを残す。

- 受け入れ条件・`Done when`・`Not done if`
- 挙動の決定事項（「〜のときは〜する」）。表や箇条書きの中のものも含める
- 互換性・移行の条件（既存バージョン、既存ユーザー）
- `Required verification` と「Merge 前の確認」

一つの文に複数の挙動がある場合は分ける（例：「サインイン時に引き継ぐ」「ログアウト時に引き継ぐ」は別の行）。

### 3. 各行に担当の子Issueを対応づける

各行について、それを **In scope または Done when に持つ** 子Issueを探し、その子Issueの原文を引用する。

担当とみなさないもの:

- タイトルが近いだけで、本文の In scope / Done when に書かれていない
- 「別Issueで行う」「App の子Issueで行う」「#xxx のエンドポイントで行う」と書いてあるが、参照先に該当する In scope / Done when がない（宛先のない先送り）
- Out of scope に書かれている
- 閉じた子Issueだが、Done when にその行がなかった

### 4. 作るものと使う側を対応づける

子Issueが作る成果物（エンドポイント、テーブル・カラム、イベント、フラグ、シークレット、設定、共有部品）ごとに、

- 作る側（provider）の子Issue
- 使う側（consumer）の子Issue — 呼び出し・表示・利用が **Done when にある** こと

を確認する。使う側がいない成果物は、使われないまま完了扱いになる。

### 5. 検証手順が共有状態を壊さないか確認する

`Required verification` / Merge 前の確認に、元に戻せない操作が入っていないか見る。

- アカウント削除、ログアウトで作り直される状態、データ消去、購入・解約、本番データの書き換え
- 対象が共有アカウント（ストア審査用、デモ用、オーナーの実アカウント）や本番環境になっていないか

該当する場合は、使い捨てのアカウントか開発環境で行うよう、手順の修正を提案する。

## 出力

対応表と、問題の一覧を出す。

| 親の要件（原文） | 担当の子Issue | 根拠（子Issueの原文） | 状態 |
|---|---|---|---|
| 「匿名ユーザーが既存アカウントにサインインし…大きい方を引き継ぐ」 | — | — | 担当なし |

状態は次のどれか:

- **担当あり**: In scope / Done when に明記されている
- **一部**: 一部の挙動・プラットフォームだけ担当されている（足りない部分を書く）
- **担当なし**: どの子Issueにもない
- **宛先のない先送り**: 「別Issueで」と書かれているが、参照先にない
- **使う側なし**: 成果物を作る子Issueはあるが、使う子Issueがない
- **検証が危険**: 共有状態を壊す検証手順

問題ごとに、どの子Issueに何を足すか（または新しい子Issueが必要か）を **提案** として書く。親・子Issueの本文は、オーナーの了承なしに書き換えない。

## してはいけないこと

- 子Issueを閉じる前だけに確認する
- タイトルや Issue 番号の並びから、担当を推測する
- 「たぶん実装に含まれるはず」で担当ありにする。根拠の原文を引用できなければ担当なし
- 問題が見つかった子Issueを、そのまま割り当てる。担当なし・宛先のない先送り・検証が危険のどれかがあれば、割り当てる前にオーナーに報告する

## 例（SpeakGain #413、2026-10）

親 #413 は「サインイン時・ログアウト時に、利用回数は大きい方を引き継ぐ」と決めていた。#418 は「引き継ぎは #419 のエンドポイントで行う」と書き、#419 はエンドポイントを作ったうえで「アプリのUIは App の子Issue」とした。App の子Issue #422 は画面の実装だけで、エンドポイントを呼ぶ処理はどこにもなかった。全子Issueが完了してから実機で見つかった。

手順3で「宛先のない先送り」、手順4で「使う側なし」として、分割直後に見つかる。

同じ #413 の子Issue #418 の検証手順「購読中のアカウントでアカウント削除 → 同じ Google でサインイン」は、ストア審査用アカウントで実行され、審査用アカウントの購読が失われた。手順5で「検証が危険」として見つかる。
